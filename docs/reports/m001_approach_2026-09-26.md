Sep 26, 2026

## 1. Status

M001 (dense blocker + LightGBM matcher + one-owner/margin decoding) scores **0.961 on the public leaderboard**, up from 0.937 for P002, with a local-to-public gap of 0.0105 instead of 0.040.

| System | Local validation (macro F0.5) | Public leaderboard | Local-public gap |
| --- | ---: | ---: | ---: |
| P002 (previous: lexical K10 + LightGBM + XLM-R, one-owner margin 0.48) | 0.9771 (10k cohort, 20% index) | 0.937 | -0.040 |

What the remaining gap likely means: test S1 is 38.3% US, 46.8% India, 15.0% France. If US and India score on test what they score on holdoutB (0.9728 / 0.9697), France would be about 0.90. Test is also denser than train (5.75 vs 4.68 S2/S3 records per S1), which can lower US/India slightly. Without labels the two causes cannot be separated exactly.

The blocker is no longer the bottleneck: a perfect matcher on our candidates would score 0.9982 on holdoutB, so ~0.027 of headroom sits in matching and decoding.

## 2. Validation protocol

Validation mimics test conditions: unseen S1, full-size search indexes, and every train S1 competing in decoding.

**Split** (`experiments/splits/s1_split_v1.tsv`): an S1 is in `holdout` when `int(sha1(entity_id)[:8], 16) % 5 == 0` (20%), else `dev`. Each S1 keeps all its true S2/S3 matches. Holdout is halved again by a second hash, `int(sha1(entity_id)[8:16], 16) % 2`:

| Part | Train S1 | Used for | Never used for |
| --- | ---: | --- | --- |
| dev | 1,765,725 | Training the dense blocker model (800k pairs); scored only as one-owner competitors | Matcher training or tuning |
| holdoutA | ~220,000 | LightGBM training (2-fold out-of-fold) and decoder tuning (tau, delta) | - |
| holdoutB | 220,319 | Final evaluation, scored once with everything frozen | Any training or tuning |

Why holdoutA trains the matcher: the dense model was trained on dev pairs, so dev candidates look easier than test candidates. Both holdout halves are unseen by the blocker, like test.

**Three rules that make the number trustworthy (all were violated by the earlier P002 validation):**

1. Full-density search: every query searches all train S2/S3 of its country (US 6.2M, India 4.1M records), not a ~20% subset. On a 20% index the same blocker's oracle is inflated from 0.9775 to 0.9887.
2. Real competition in decoding: blocking and scoring run for all 2.2M train S1, so one-owner decoding sees every competing S1 for an aux record. With only a 10k cohort, another S1 within 0.10 cosine of the true owner almost never appears (0.05-0.2% vs 6% US / 16% India in the full population).
3. Tuning and evaluation are disjoint: decoder thresholds come from holdoutA out-of-fold scores; holdoutB is touched once.

**Metric:** official macro F0.5 per S1, singletons included (empty prediction on a true singleton = 1.0, any prediction = 0.0).

## 3. Pipeline architecture (M001)

Four stages, all within literal country equality (country is an open set; France runs the same code): dense blocking, candidate assembly, LightGBM pair scoring, one-owner + margin decoding.

```
all S1, S2, S3 records
  -> [1] embed each record once (fine-tuned multilingual-e5-base)
  -> [1] FAISS IVF-Flat per country: forward S1 -> top-10 S2 and top-10 S3; reverse each S2/S3 -> top-2 S1
  -> [2] candidates = forward top-10/source  U  reverse top-1 (capped at 10 per S1)      ~20.3 per S1
  -> [3] 31 pair features -> LightGBM -> p(match) per candidate pair
  -> [4] one-owner + margin: each S2/S3 goes to its best S1 if p >= 0.6 and p - p_second >= 0.3
  -> matching_results.tsv  (candidate_pairs.tsv = every pair scored in [3])
```

**[1] Blocker v1.** Model `intfloat/multilingual-e5-base` (278M, MIT), fine-tuned as a bi-encoder: MultipleNegativesRankingLoss, 800k true pairs from dev S1, 1 epoch, batch 256, lr 3e-5, max_seq_length 64, bf16 (~30 min on one A100). Record text: `query: {business_name} | {business_address}`. Index: FAISS GPU IVF-Flat, inverted lists = power of two near 4 x sqrt(N), nprobe 64 (~1% of an index scanned per query). Full details and blocking experiments are in the earlier report "Scalable Blocking for Business Entity Resolution" (`reports/blocking_report_2026-09-26.md`).

**[2] Candidate assembly.** Forward pairs keep their rank and cosine; reverse pairs are the aux record's top-1 S1, capped at 10 per S1 by cosine. The reverse top-2 is kept only to compute competition features.

**[3] Features (31, country-agnostic, no country one-hot).**

| Group | Features |
| --- | --- |
| Retrieval | `score` (dense cosine), `fwd_rank` (99 if reverse-only), `is_rev`, `rank_in_s1`, `s1_n` (candidates of this S1), `s1_max`, `gap_s1` (score minus the S1's best) |
| Aux competition | `aux_top1_score`, `aux_top2_score`, `aux_margin` (top1 - top2 over all S1), `is_aux_top1` (this S1 is the aux's best S1), `gap_aux` (score minus the aux's best), `aux_fanout` (candidate lists containing this aux) |
| Name strings (rapidfuzz) | on normalized names: `nm_ratio`, `nm_tset`, `nm_tsort`, `nm_partial`; on anyascii-transliterated names: `tr_tset`; on phonetic skeletons: `sk_ratio` |
| Address strings | on abbreviation-normalized addresses: `ad_ratio`, `ad_tset`, `ad_partial` |
| House numbers | `num_state` (1 equal / 0 conflict / 2 missing on a side), `num1_sim` (normalized Levenshtein of first numbers), `num_jaccard` (all numbers), `num_prefix` (one truncates the other) |
| Metadata | `is_s3`, `native_i` (Indic-script aux name), `empty_addr_i`, `len_ratio`, `nlen` |

**LightGBM:** binary objective, lr 0.05, 255 leaves, min_data_in_leaf 200, feature/bagging fraction 0.8, lambda_l2 1. Trained on holdoutA pairs with a 2-fold split by S1 hash for out-of-fold scores (early stopping per fold); the final model (766 trees) uses 1.1 x the mean best iteration on all holdoutA. Importance by gain: `gap_aux` 40.9%, `score` 32.2%, `num_jaccard` 6.4%, `len_ratio` 2.3%, `nm_tsort` 2.1%, `num_state` 2.0%, `is_rev` 1.7%, then name/address/number string features at about 1% each. The competition feature (how far this S1 is from the aux record's best S1) matters most.

**[4] Decoding (one-owner + margin).** For every S2/S3 record, rank its candidate S1 by p. Accept the best S1 only if p >= tau and p - p_second >= delta; otherwise the record stays unassigned. tau = 0.6 and delta = 0.3 were chosen on holdoutA out-of-fold scores with all train S1 competing.

## 6. What we did before M001 and what we learned

The biggest gains came from fixing validation and replacing lexical blocking with a fine-tuned dense retriever; several plausible ideas did not help.

**Diagnosis of P002 (0.977 local, 0.937 public).**

- Validation searched a ~20% index: oracle of the same blocker 0.9887 there vs 0.9775 at full size.
- One-owner decoding was tuned on a 10k-S1 cohort, so competing S1 almost never appeared; the 0.48 owner margin then rejected many true matches on test (53% of test aux assigned vs 74% matched in train; France 48%).
- The XLM-R cross-encoder was trained on 98k of 7.6M available positives, with negatives only from forward retrieval.

**Blocking experiments (details in the blocking report).**

| ID | Finding |
| --- | --- |
| B001 | 13-24% of India S2/S3 names are in Indic scripts. Normalized names + raw (not punctuation-stripped) addresses: +0.0023 oracle. Native-script phonetic skeleton stream: +0.0005-0.0010. |
| B002-B003 | Reverse search (aux to S1) is the best lexical idea: +0.007 oracle for +2 candidates. It creates hub S1 with up to 7,900 candidates, so it needs a cap. |
| B004 | A LightGBM re-ranker over a 105-candidate lexical pool keeps its ceiling (0.9932) with 10 candidates. |
| B005 | Fine-tuned dense e5 retrieval beats every lexical setup: 0.9960 oracle at 6.7 candidates (exact search). |
| B007 | Number-aware address view (`#25#` tokens): +0.0017 oracle; France address agreement 0.40 to 0.80. Abbreviation table: neutral/slightly negative on US/India. |
| B008 | FAISS IVF-Flat nprobe 64 loses only 0.0006 oracle vs exact at top-10; IVF-PQ loses 0.002-0.004. |

**France (no labels).** Same noise generator as US/India, plus street abbreviations (`R.`, `AV`, `BD`), dropped house numbers (86% of S1 addresses start with a number vs 69% of S2/S3), region replaced by department, and very dense cities (Bordeaux 37k S1). Char n-grams nearly ignore short house numbers. The dense model shows no France collapse on label-free checks (top-1 same house number 88% vs 81% US).

**Did not help / avoid:**

- Replacing the name stream with a phonetic skeleton (0.9751 vs 0.9775).
- Transliterating addresses (loses discriminative punctuation such as `1-D-206`).
- Asymmetric name/address K in lexical blocking.
- Compressed IVF-PQ at this data size.
- Synthetic French pairs (team decision: not used).
- Any validation with a shrunken index or a small decoding cohort.

## 7. Open problems and ideas to try

The matcher and decoder hold the headroom (0.9715 vs a 0.9982 ceiling), and France is the likely main source of the public gap. Every idea should be validated with the Section 2 protocol and reported as holdoutB macro F0.5 next to 0.9715.

| # | Idea | Problem it targets | Expected gain | Notes |
| --- | --- | --- | --- | --- |
| 1 | **Cross-encoder matcher** (e.g. `FacebookAI/xlm-roberta-base` or `microsoft/mdeberta-v3-base`, both MIT) on the top 5-8 LightGBM candidates per S1, fused with LightGBM (learned fusion, not a fixed 0.6/0.4) | Recall loss (0.945) and 1-match S1 (0.925); reads both records jointly, handles scripts and French | +0.005-0.015 | Train on holdoutA candidates (hard negatives from our blocker, including competing-S1 negatives); keep holdoutB untouched |
| 2 | **France diagnostics** on test predictions: score, margin and rejection-rate distributions by country | Is France the main loss? Is its calibration shifted? | enables #3 | Label-free; compare with US/India test |
| 3 | **France-safe address features**: street + house number similarity ignoring the region/department part; number-aware address view (`#25#` tokens, B007); abbreviation-normalized street types | Dense French streets, region to department swaps | +0.002-0.008 total if France is the problem | All country-agnostic; validate no loss on US/India |
| 4 | **S1-level features / decoding** for singletons and 1-match S1: number of strong candidates, whether the best candidate is contested, a small "predict empty" model | Singleton accuracy 0.947, 1-match 0.925 | +0.002-0.005 | Tune on holdoutA only |
| 5 | **More matcher training data**: retrain the dense blocker on half of dev and train the matcher on the other half (plus holdoutA) | Matcher trained on only ~220k S1 | +0.001-0.003 | Requires re-embedding train (~1 h) |
| 6 | **Dense hard-negative fine-tuning** (same street + different number, same name + different address) | Look-alike neighbours in blocking and in the `score` feature | small-medium | Training-only change |
| 7 | **Smaller candidate set**: re-rank the ~20 candidates and keep 5-10 per S1 for `candidate_pairs.tsv` | Organizers rank smaller candidate sets higher | ranking, not F0.5 | B004 shows little oracle loss at 10 |
| 8 | **Name abbreviation / legal-form normalization** (`Pvt`, `Ltd`, `LLC`, `Corp`, `SARL`, `SAS`) as features | Organizer-listed name noise | low-medium | Untested |

Things to keep: country equality, full-density validation, all-S1 decoding, one-owner + margin decoding tuned out-of-fold, and exact search only for measurement (never in the submission).
